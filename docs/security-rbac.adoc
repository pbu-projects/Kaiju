== Practical Intent and Community Value

Kaiju serves community volunteers, neighborhood organizations, and regional coordinators. 
Protecting user privacy, maintaining trusted regional boundaries, and preventing accidental or unauthorized changes are essential to building community trust.

Rather than relying on vague, one-size-fits-all administrator badges, Kaiju separates permissions into specific, practical actions. 
This ensures that a neighborhood team leader can easily manage volunteer shifts for their local park cleanup without ever having the ability to alter regional civic boundaries or view private user records across the entire state.

== Real-World Roles and Clear Boundaries

Every person interacting with the platform operates with an assigned role that fits their practical day-to-day responsibilities:

[cols="25%,35%,40%",options="header"]
|===
| Role | Who They Are | What They Can Do in Practice

| *Platform Administrator* +
(`GLOBAL_ADMIN`)
| Global stewards (like Sarah or Gary) responsible for system reliability and platform-wide integrity.
| Manage platform-wide settings, ingest official government boundaries, manage user accounts, and resolve cross-regional issues.

| *Regional Director* +
(`REGION_DIRECTOR`)
| Local civic leaders (like Rachel or Daniel) who guide community initiatives across a state, county, or city district.
| Create and update civic boundaries in their jurisdiction and approve community service projects within their assigned territory. They cannot view or edit user accounts across other regions.

| *Regional Agent* +
(`REGION_AGENT`)
| Field coordinators (like Samuel or Connie) supporting local directors.
| Review and approve community projects within their geographic area. They cannot alter regional boundary lines or manage system settings.

| *Organization Manager* +
(`ORG_ADMIN` / `ORG_MANAGER`)
| Community partners (like Nathan or Laura) running local charities, food pantries, or service clubs.
| Create community projects, schedule volunteer shifts, and coordinate team members for their organization.

| *Community Volunteer* +
(`STANDARD_USER`)
| Neighbors (like Victor or Alice) offering their time and energy to help others.
| Discover nearby service opportunities, register for shifts, and track their personal volunteering commitments. They cannot access administrative tools.
|===

== Two-Layer Security Architecture

Kaiju separates access control into two complementary layers: **High-Level Roles** and **Discrete Capability Permissions**.

=== Layer 1: Identity Providers and Initial Onboarding
When someone signs into Kaiju, they authenticate through an OpenID Connect identity provider such as https://goauthentik.io/[Authentik] (or Okta, Keycloak, or Google in production environments).

1. *Cryptographic Verification*: The incoming login token is cryptographically verified against the identity provider's published key set (JWKS) to guarantee it has not been altered or forged.
2. *Group Translation*: The identity provider passes along the groups the user belongs to (such as `Kaiju Global Admins` or `Kaiju Region Directors`). 
3. *Just-In-Time Account Setup*: If this is the user's first time visiting Kaiju, `IdpRoleMapper` translates their identity group into the appropriate starting role and creates their local database account seamlessly.

=== Layer 2: Discrete Capability Permissions
Titles and role names can mean different things across various organizations. 
To prevent ambiguity, Kaiju maps every system role to a concrete list of specific capability permissions:

[cols="30%,70%",options="header"]
|===
| Role | Allotted Capability Permissions

| *GLOBAL_ADMIN*
| `system:admin`, `system:user-manage`, `region:manage`, `org:manage-users`, `org:edit`, `org:read`, `project:approve`, `project:reassign`, `project:create`, `project:read`, `project:update`, `project:delete`

| *REGION_DIRECTOR*
| `region:manage`, `project:approve`, `project:reassign`, `org:read`, `project:create`, `project:read`, `project:update`, `project:delete`

| *REGION_AGENT*
| `project:approve`, `project:reassign`, `org:read`, `project:create`, `project:read`, `project:update`, `project:delete`

| *STANDARD_USER*
| `org:read`, `project:create`, `project:read`, `project:update`, `project:delete`
|===

When an API request arrives, the authentication factory attaches these exact permission strings to the active security context. 

== Declarative Route Protection

Controllers protect endpoints by declaring the exact permission required for the action, using https://micronaut-projects.github.io/micronaut-security/latest/guide/index.html[Micronaut Security] annotations.

For example, creating a new civic boundary requires the `region:manage` permission:

[source,java]
----
@Secured({SYSTEM_ADMIN_CLAIM, REGION_MANAGE_CLAIM})
@Post
public AdministrativeRegion addAdministrativeRegion(...) {
    // Both Platform Admins and Regional Directors can reach this endpoint
}
----

Meanwhile, browsing sensitive platform account lists requires the stricter `system:user-manage` permission:

[source,java]
----
@Get
@Secured(SYSTEM_USER_MANAGE_CLAIM)
public CursoredPage<User> getUsers(...) {
    // Only Platform Admins hold this capability; Regional Directors and Volunteers receive 403 Forbidden
}
----

Because endpoints check specific permissions rather than hardcoded role names:
- Security rules are self-documenting and auditable directly in code.
- Individual permissions can be tailored or granted without needing to rewrite controller logic.

== Live Database Authority and Instant Protection

In many distributed systems, updating a user's permissions requires them to log out and log back in, or wait for an access token to expire. 
If an account is compromised or someone leaves a leadership role, that delay represents a real security risk.

In Kaiju, the PostgreSQL database is the active source of truth for user permissions:

1. *Every Request Checks the Live Account*: When an authenticated request arrives, Kaiju verifies the token's cryptographic signature, looks up the active user record in PostgreSQL, and applies the user's current permissions.
2. *Instant Promotion*: If an administrator promotes a volunteer to a Regional Director in the database, the volunteer immediately gains access to regional management tools on their very next request using their existing login token.
3. *Instant Demotion and Revocation*: If an administrator demotes an account or removes elevated privileges, the user is immediately turned away (receiving a `403 Forbidden`) on their very next action. No cached token can bypass the live database guardrail.

== Verification and Testing

This security model is continuously tested under live conditions to guarantee reliability:

- *Live Identity Provider Integration*: Automated tests log genuine test personas through Authentik, minting genuine RS256 signed tokens to test real network flows.
- *Privilege Containment Tests*: Every administrative level is tested to prove that unauthorized actions are turned away at the door with clean `403 Forbidden` responses.
- *Dynamic Role Reflection Tests*: Automated tests confirm that changing a user's role in the database instantly updates their live clearance under the wire without requiring a new token.
