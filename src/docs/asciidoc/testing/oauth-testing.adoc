A practical guide for QA engineers and developers explaining how Kaiju tests login flows, token parsing, and data-driven test matrices.

== Why We Test Logins This Way

Logging into an application sounds simple, but real-world authentication touches several moving parts: browser redirects, cookies, digital signatures, and database accounts.

In Kaiju, we avoid using fake mocks for login tests. Instead, we test against a live https://goauthentik.io/[Authentik] identity provider running in https://www.docker.com/[Docker]:

* **Real Redirect Chains**: When users log in, their browser bounces between Kaiju and Authentik with HTTP `302 Found` redirects. Real tests ensure redirect query parameters match what identity servers expect.
* **Real Security Cookies**: Browsers rely on cookies to remember who is logged in and to protect against login tampering. Testing against real HTTP endpoints ensures cookies are set with secure flags and cleared properly.
* **Real Digital Signatures**: Authentik signs user identity tokens using asymmetric keys (RS256). The identity server signs tokens with its private key, and Kaiju verifies signatures using the downloaded public key (JWKS) without needing shared secrets. Testing against a live service proves that signature checks succeed before code reaches production.
* **Two Layers of Testing**: We test authentication across two layers: integration tests for token parsing and database lookup backed by PostGIS in Testcontainers, and end-to-end integration tests for network communication with live Authentik.

== What Is Being Tested

Our test suite verifies authentication across two complementary test specifications:

=== Live OIDC Integration (`AuthentikOidcIntegrationSpec`)

This integration test runs a complete browser login flow against a live Authentik container and a real https://www.postgresql.org/[PostgreSQL] database:

1. **Login Initiation (`GET /oauth/login/authentik`)**: The client calls the login start point and verifies that Kaiju returns a `302 Found` redirect to Authentik. It checks that three temporary security cookies are created:
   * `OAUTH2_STATE`: Protects against cross-site request forgery (CSRF).
   * `OAUTH2_PKCE`: Stores the code verifier for https://datatracker.ietf.org/doc/html/rfc7636[Proof Key for Code Exchange (PKCE)].
   * `OPENID_NONCE`: Protects token signatures against replay attacks.
2. **Authorization Code Callback (`GET /oauth/callback/authentik`)**: The test simulates the browser returning from Authentik with an authorization code and passes back the security cookies.
3. **Backchannel Token Exchange**: Kaiju calls Authentik over HTTP to exchange the code for signed tokens. The test verifies that Authentik accepts the code and verifier.
4. **Just-In-Time (JIT) Provisioning**: The test uses a brand-new volunteer persona, `Jenny New` (`jenny.new@kaiju.local`). Jenny exists in Authentik but has no row in PostgreSQL. The test verifies that Kaiju automatically creates her volunteer record with the standard role (`STANDARD_USER`).
5. **Session Cookie Issuance**: The test verifies that Kaiju responds with a `303 See Other` redirect and sets a secure `JWT` session cookie while clearing temporary login cookies (`Max-Age=0`).
6. **Downstream API Access**: The test sends a follow-up request to a protected endpoint (`/projects`) using the `JWT` session cookie to prove that https://micronaut-projects.github.io/micronaut-security/latest/guide/[Micronaut Security] recognizes the session without needing bearer tokens.
7. **Automatic Cleanup**: When the test finishes, Jenny's newly created account is removed from PostgreSQL so future test runs start clean.

=== Token and Claim Mapping Tests (`AuthentikAuthenticationMapperSpec`)

This test specification verifies how raw token responses and claim dictionaries convert into Micronaut authentication objects and database accounts:

* **Token Preservation**: Verifies that the signed ID token string is stored in authentication attributes under the `openIdToken` key so that cookie serializers can create the session cookie.
* **Email Verification**: Verifies that `email_verified` is mapped to a true boolean, preventing unverified email addresses from gaining access.
* **Claim Extraction**: Verifies that user email, roles, and names are correctly pulled from token claims.
* **Combinatorial Matrix Testing**: Uses Groovy's `.combinations()` method to verify all 32 permutations of token strings, verification formats, and extra fields. (See the General Testing Conventions chapter for full details on our combinatorial testing rules).

== QA Verification Playbook

=== Running the Token and Claim Mapping Tests

To run the token and claim mapping test suite:

[source,bash]
----
./gradlew test --tests "lol.pbu.kaiju.security.AuthentikAuthenticationMapperSpec"
----

Expected result: Tests spin up PostGIS via Testcontainers, apply Flyway migrations, and execute 55 test specifications green.

=== Running the Live Integration Tests

To run the full browser redirect and database provisioning test against live Docker containers:

[source,bash]
----
./gradlew test --tests "lol.pbu.kaiju.security.AuthentikOidcIntegrationSpec"
----

Expected result: The test automatically spins up PostGIS in Docker, contacts the live Authentik instance, executes the login redirect loop, verifies Jenny's row in PostgreSQL, and cleans up.
